# ADR-016: Hand-Authored Alembic Migrations, StrEnum-as-String, Schema-via-Upgrade

**Date:** 2026-07-20

## Context

Schema evolution needs to be reviewable, deterministic, and actually exercised — not a pile of
autogenerated revisions nobody reads and nobody runs until production. Three recurring hazards:

- **Autogenerate drift** — a model changes but no migration is written, so the running schema and the
  ORM disagree.
- **PG enum rigidity** — native PostgreSQL enums make adding/removing a value a migration in itself,
  which is heavy for role/type value sets that evolve.
- **Untested migrations** — building the test schema from `create_all` means migrations never run in
  CI, so a broken migration ships undetected.

## Decision

- **Hand-author Alembic revisions** with 12-char slugs and explicit `down_revision` chaining — match
  the existing style rather than relying on raw autogenerate output.
- Store role/type **enums as plain `String` (StrEnum)**, not PG enums, so value sets evolve without a
  schema migration.
- **Build the test schema with `alembic upgrade head`** (not `create_all`), so **every CI test run
  exercises the full migration chain**; `tests/test_migrations.py` fails the build on ORM↔migration
  drift via `alembic check`.
- A new model module must be **imported in `alembic/env.py`** (or it's invisible to autogenerate) and
  needs **its own migration** (or it has no table and every test touching it fails).

## Consequences

- **Migrations are exercised on every CI job**: a broken or missing migration fails the build, not
  production. The test schema *is* the migrated schema.
- **Reviewable history**: hand-authored revisions with explicit chaining read as intentional schema
  changes rather than opaque autogenerate dumps.
- **Cheap enum evolution**: adding a role/type value is a code change, not a schema migration — at the
  cost of losing the database-level value constraint a PG enum would give.
- **`alembic check` has blind spots**: it doesn't catch `server_default`s or CHECK constraints, so
  those must be asserted by hand in tests ([AGENTS.md](../../AGENTS.md)).
- **Two easy-to-miss steps per model**: the `env.py` import and the migration. Both fail loudly (in
  autogenerate and in tests respectively), which is why they're documented conventions.
